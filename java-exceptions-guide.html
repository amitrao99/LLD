Java Exceptions: A Practical Guide for the Working Engineer

1. The Exception Hierarchy (Quick Refresher)

Throwable ├── Error (Don't catch these - JVM problems like OutOfMemoryError) └── Exception ├── RuntimeException (Unchecked) │ ├── NullPointerException │ ├── IllegalArgumentException │ ├── IllegalStateException │ └── ... └── Other Exceptions (Checked) ├── IOException ├── SQLException └── ...

Checked vs Unchecked

Checked Unchecked
Extends Exception directly Extends RuntimeException
Compiler forces you to handle or declare No compile-time enforcement
Recoverable conditions (file not found, network issues) Programming errors (null access, bad arguments)
Must use throws clause or try-catch Optional handling
Your LedgerException extends Exception directly → it's checked. Callers must handle it.

2. Anatomy of an Exception

Every exception has these key components:

java
public class Throwable {
    private String detailMessage;      // The "what happened" message
    private Throwable cause;           // The underlying exception (if any)
    private StackTraceElement[] stackTrace;  // The "where it happened"
}

The Three Pillars

1. Message — Human-readable description

java
throw new Exception("User not found with ID: 123");
//                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ this is getMessage()

2. Cause — Exception chaining (preserving the root cause)

java
try {
    database.query(...);
} catch (SQLException e) {
    throw new LedgerException(ErrorCode.DB_ERROR, "Query failed", e);
    //                                                            ^ cause preserved
}

3. Dissecting Your LedgerException

Let's break down what your code is doing and why:

java
public class LedgerException extends Exception {
Decision: Extends Exception → checked exception. This is appropriate for a ledger system where errors (insufficient funds, invalid accounts) are expected conditions that callers must handle.

The Fields

java
private final ErrorCode errorCode;  // Structured, machine-readable identifier
private final String details;       // Runtime-specific context

Why both?

  • ErrorCode is stable, loggable, mappable to HTTP status → for systems
  • details is dynamic, contextual → for debugging

Example:

java
throw new LedgerException(ErrorCode.INSUFFICIENT_FUNDS, "Attempted: £500, Available: £123.45");
//                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                        Stable code for API response   Context for logs/debugging

The Constructors — The Rule of Three

java
// 1. Minimal — when the error code says it all
public LedgerException(ErrorCode errorCode) {
    super(errorCode.getMessage());  // Parent gets the message
    this.errorCode = errorCode;
    this.details = null;
}

// 2. With context — the common case
public LedgerException(ErrorCode errorCode, String details) {
    super(errorCode.getMessage() + ": " + details);  // Concatenated for getMessage()
    this.errorCode = errorCode;
    this.details = details;
}

// 3. With cause — for exception chaining
public LedgerException(ErrorCode errorCode, String details, Throwable cause) {
    super(errorCode.getMessage() + ": " + details, cause);  // ← Cause passed to parent
    this.errorCode = errorCode;
    this.details = details;
}
Critical: The third constructor preserves the cause chain. Without it, you lose the stack trace of the original exception.

The API-Friendly Conversion

java
public ErrorResponse toErrorResponse() {
    return new ErrorResponse(
        errorCode.getCode(),      // "INSUFFICIENT_FUNDS"
        errorCode.getMessage(),   // "Insufficient funds for transaction"
        details,                  // "Attempted: £500, Available: £123.45"
        errorCode.getHttpStatus() // 400
    );
}

This pattern keeps your exception useful both internally (for logging, stack traces) and externally (for API responses). The exception itself carries everything needed to generate a proper error response.

4. When to Create Custom Exceptions

Create a custom exception when:

  • You need to attach domain-specific data (error codes, entity IDs, etc.)
  • You want a clear type for catch blocks (catch (LedgerException e))
  • You need to map exceptions to specific API responses
  • Multiple error conditions share common handling patterns

Don't create a custom exception when:

  • Standard exceptions suffice (IllegalArgumentException, IllegalStateException)
  • You'd just be wrapping with no added value
  • It's a one-off error with no special handling needs

5. Best Practices

Creating Custom Exceptions

1. Choose checked vs unchecked deliberately

java
// Checked: "Caller can and should recover from this"
public class InsufficientFundsException extends Exception { }

// Unchecked: "This is a bug, fail fast"
public class InvalidAccountStateException extends RuntimeException { }

2. Always provide the cause-accepting constructor

java
// Without this, you lose the original stack trace
public LedgerException(ErrorCode code, String details, Throwable cause) {
    super(code.getMessage() + ": " + details, cause);  // ← cause passed up
    // ...
}

3. Make exceptions immutable

java
private final ErrorCode errorCode;  // ← final
private final String details;       // ← final

4. Override toString() for better logging

java
@Override
public String toString() {
    if (details != null) {
        return String.format("%s - %s", errorCode, details);
    }
    return errorCode.toString();
}
// Logs: "INSUFFICIENT_FUNDS(400) - Attempted: £500, Available: £123.45"

5. Include what you need, nothing more

java
// Good: Relevant context
throw new LedgerException(ErrorCode.ACCOUNT_NOT_FOUND, "accountId=" + accountId);

// Bad: Too much (security risk, log bloat)
throw new LedgerException(ErrorCode.ACCOUNT_NOT_FOUND, account.toString());

Throwing Exceptions

1. Throw early, at the point of detection

java
public void transfer(Account from, Account to, Money amount) throws LedgerException {
    if (from == null) {
        throw new IllegalArgumentException("Source account cannot be null");  // Throw immediately
    }
    // ... rest of method
}

2. Include actionable context

java
// Bad
throw new LedgerException(ErrorCode.VALIDATION_ERROR, "Invalid input");

// Good
throw new LedgerException(ErrorCode.VALIDATION_ERROR, 
    "Amount must be positive, got: " + amount);

3. Don't use exceptions for flow control

java
// Bad — exceptions are expensive
try {
    return accounts.get(id);
} catch (NotFoundException e) {
    return createDefault();
}

// Good — check first
if (accounts.contains(id)) {
    return accounts.get(id);
}
return createDefault();

Catching Exceptions

1. Catch specific exceptions first

java
try {
    ledger.process(transaction);
} catch (InsufficientFundsException e) {
    // Handle specifically
} catch (LedgerException e) {
    // Handle other ledger errors
} catch (Exception e) {
    // Last resort
}

2. Never catch and ignore silently

java
// Never do this
try {
    riskyOperation();
} catch (Exception e) {
    // 🦗 crickets
}

// At minimum
catch (Exception e) {
    log.error("Operation failed", e);
}

3. Wrap exceptions at layer boundaries

java
// In your service layer
public Account getAccount(String id) throws LedgerException {
    try {
        return repository.findById(id);
    } catch (SQLException e) {
        // Don't leak SQL details to callers
        throw new LedgerException(ErrorCode.DB_ERROR, "Failed to fetch account", e);
    }
}

4. Use try-with-resources for cleanup

java
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {
    // ...
}  // Auto-closed even if exception thrown

5. Don't catch Throwable or Error

java
// Don't do this — Errors are JVM-level problems
catch (Throwable t) { }

// Acceptable
catch (Exception e) { }

The ErrorCode Enum Pattern (Your Approach)

public enum ErrorCode {

Why this works well:
  • Centralized error definitions
  • Type-safe (can't misspell error codes)
  • Easy to map to HTTP responses
  • Easy to document for API consumers

Exception Translation at Boundaries

java
@RestControllerAdvice
public class GlobalExceptionHandler {
    
    @ExceptionHandler(LedgerException.class)
    public ResponseEntity<ErrorResponse> handleLedger(LedgerException e) {
        log.warn("Ledger error: {}", e.toString());
        return ResponseEntity
            .status(e.getHttpStatus())
            .body(e.toErrorResponse());
    }
}

How super(message) Works in Exception Constructors

The super(...) call sets the message in the parent class — it doesn't append to anything because there's nothing there yet. The parent's detailMessage field starts as null, and your super() call initializes it.

What's Actually Happening

java
// Inside Throwable (the root of all exceptions)
public class Throwable {
    private String detailMessage;  // Starts as null
    
    public Throwable(String message) {
        this.detailMessage = message;  // Your super() call triggers this
    }
    
    public String getMessage() {
        return detailMessage;  // Returns whatever was set
    }
}

Three Scenarios

Scenario 1: Using the first constructor (no details)

java
throw new LedgerException(ErrorCode.ACCOUNT_NOT_FOUND);

Constructor called:

java
public LedgerException(ErrorCode errorCode) {
    super(errorCode.getMessage());  // super("Account not found")
    this.errorCode = errorCode;
    this.details = null;
}

Result:

java
e.getMessage()  → "Account not found"
e.getDetails()  → null

Scenario 2: Using the second constructor (with details)

java
throw new LedgerException(ErrorCode.ACCOUNT_NOT_FOUND, "accountId=ABC123");

Constructor called:

java
public LedgerException(ErrorCode errorCode, String details) {
    super(errorCode.getMessage() + ": " + details);  // super("Account not found: accountId=ABC123")
    this.errorCode = errorCode;
    this.details = details;
}

Result:

java
e.getMessage()  → "Account not found: accountId=ABC123"  // The concatenated string
e.getDetails()  → "accountId=ABC123"                     // Just the details part

Scenario 3: Using the third constructor (with cause)

java
try {
    database.findAccount(id);

java
public LedgerException(ErrorCode errorCode, String details, Throwable cause) {
    super(errorCode.getMessage() + ": " + details, cause);  // super("Database error: query failed for id=123", sqlEx)
    this.errorCode = errorCode;
    this.details = details;
}

Result:

e.getDetails()  → "query failed for id=123"
e.getCause()    → SQLException("Connection refused")

Visual Summary

LedgerException constructor │ ▼ super(errorCode.getMessage() + ": " + details) │ ▼ Throwable constructor receives: "Account not found: accountId=ABC123" │ ▼ Sets: this.detailMessage = "Account not found: accountId=ABC123" │ ▼ getMessage() returns exactly that string
The key insight: You're constructing the message yourself before passing it up. The parent just stores whatever string you give it.
